# Connectors and keychain secrets

Each outside source is a connector: a manifest (id, label, auth kind, the secrets it needs, the ledger counts it feeds) plus an adapter (test connection, pull). `src/server/connectors/registry.ts` finds every folder under `src/server/connectors/` on its own. Secrets are sealed by the macOS Keychain through Orca's `SecretStore`; on boot a legacy plaintext `secrets` row moves to `sealed_secrets`. Architecture: `documents/architecture/connectors.md`.

## Sub-features

- Bridge `listConnectors`: every connector, its status (`configured`, `needs-setup`, `not-connected`) and where each secret comes from (`keychain`, `db`, `env`, `none`), never a value.
- Bridge `testConnector(id)`: the adapter's connection check, recorded in `connector_status`; a manifest-only connector answers not connected. Bridge `pullConnector(id)`: the adapter's pull, recorded the same way; only the sidecar card has a Pull button, so agents and journeys pull the others through the bridge. Each card shows one state (`ready`, `partial`, `error`, or `not-connected` when setup is missing): a failed check's error, else the last pull's outcome, which stays until the next pull, with its message and a "Details: ..." line. A passing check never clears a pull's error or partial. A sync scoped to some channels is not recorded, and a pull that loses to a running sync fails with "A sync is already running" and records nothing. It survives a restart. While a Re-check runs, the card alone reads Checking.
- IG sidecar (`ig-sidecar`) has its own card (`sidecar-source-card.tsx`), one view per prototype frame, named in the card's `data-view`: `off`, `starting`, `not-connected`, `form`, `testing`, `ready`, `pulling`, `done`, `stopped`, `limited`, `limited-test`, `error`, `off-mid`. `data-state` is the card state (`checking` while a card test runs).
  - The switch (`sidecar-switch`) calls `startSidecarAction` or `stopSidecarAction`; off sets `off_at`, and the card reads `off` until it is switched on.
  - Test connection (`sidecar-test`) calls bridge `sampleConnector`: the adapter's `sample()`, one `/health` plus one `/profile` of the sidecar's own handle, recorded with its line ("@handle · N followers · N posts"). An Instagram limit records `retry_after` and the button stays off until then.
  - Enter or Change session id (`sidecar-enter`) opens the form (`sidecar-session-form`, `sidecar-session-input`). Nothing tests on paste. `sidecar-form-test` calls `testSidecarSessionAction`: `POST /sample-session`, which tries the id on a throwaway client and adopts nothing. `sidecar-form-check` shows Testing, the sample, or the refusal (`data-check`). `sidecar-form-save` stays off until a test passes, then calls `saveSidecarSessionAction`: the id is stored and the sidecar adopts it (`POST /login-by-session`). `sidecar-form-cancel` discards the id. A saved id closes the form even when the sample after it fails; the card then shows that error. Not connected also shows `sidecar-session-help` ("How to get a session id"), which opens the form with the cookie steps (`sidecar-session-hint`). The limited window's marks are `sidecar-limit-mark`.
  - Pull rivals (`sidecar-pull`) calls `startSyncAction()` with no channel ids, a card pull. The card polls `getSyncProgressAction` once a second while the row is `pulling` and renders `source-pull-progress` (`source-pull-current`, `source-pull-count`, `source-pull-elapsed`, `source-pull-stop`, and `source-pull-long` after 2 minutes). Stop calls `cancelSyncAction`; the rival in hand finishes. The summary is `source-pull-summary`. Pull the rest (`sidecar-pull-rest`) passes `skipFreshWithinMinutes`, so rivals that pull already updated are left out.
- Boot migration: legacy rows move to the keychain, a failed move keeps the row and logs `secrets.keychain_move_failed`.
- Polar (`polar`): its own card, `PolarSourceCard`. Enter access token opens a token form inside the card; nothing tests on paste. Test connection calls `testPolarTokenAction` (`GET /v1/organizations` on `POLAR_API_URL`) and shows Testing, then "✓ Token works · organization <name>" or the error; Save turns on only after a pass and calls `savePolarTokenAction`, which does not call Polar. Ready shows "Organization <name> · tested HH:MM" and "Pulling orders comes in a later release.", with Test connection and Change token; no Pull button.
- Umami: its own card. Connect Umami (`umami-enter`) opens the dialog (`umami-form`, `umami-addr-input`, `umami-key-input`, `umami-key-help`). Nothing tests on typing. `umami-form-test` calls `testUmamiKeyAction` with the key as Bearer; `umami-form-check` (`data-check` `testing`, `ok`, `pick` or `err`) names the one website, or shows the picker (`umami-site-select`, `umami-site-option`) for several, or C13 or Cannot reach. `umami-form-save` stays off until a pass and a pick, then stores `UMAMI_URL`, `UMAMI_API_KEY` and `UMAMI_WEBSITE_ID` and clears the old `UMAMI_USERNAME` and `UMAMI_PASSWORD`. Ready shows `umami-sample` and `umami-last-pull`; `umami-test` is the card's Test connection. Pull funnel (`umami-pull`) shows `source-pull-progress` with `x / N pages`, Stop and the long-pull note; the summary (`source-pull-summary`) shows gift page visits, email signups and checkout clicks, the `getFunnelTotals` sums, with `umami-open-funnel`. A complete pull stores each VN day in `umami_days` and each plan keyword's `visits`, `emails` and `checkouts` in `reel_funnel`, which Funnel's gift-page step and My channel's Site column read. A stopped or partial pull stores nothing (`umami-line`, `umami-keep`). The card's `data-view` names its state.

## How to get to it (user POV)

Settings > Sources shows it: the sidebar's Sources row, or Settings, Sources. Cards are `source-card` (`data-connector-id`, `data-state`) in `source-group`s, with `source-primary` (Connect or Edit key), `source-explanation`, `source-pulls`, `source-recheck` and `source-detail`, and no Pull button (the sidecar card has its own controls, above); the key dialog is `source-key-dialog` with `source-key-input` (`data-secret-name`) and `source-key-save`.

`sources-01` (on `boards-lane.sh`) prints `ok: the sidebar's Sources opens Settings > Sources with every connector, grouped like Integrations` (card ids match `listConnectors`), `ok: only the sidecar card pulls (Pull rivals); no other card has a Pull button` (it prints each card's buttons), `ok: Connect saves a fake key, closes, and the key reads only as saved`, `ok: no bridge read carries the saved value` (it also calls `setConnectorSecret` with a field ChatbotX does not declare and is refused), `ok: the lane DB holds the key sealed, never in plaintext`, `ok: Re-check shows the connection check`, and saves `sources-01-dark`, `sources-01-light`, `sources-01-saved` and `sources-01`. It drives the ChatbotX card, which still uses the key dialog.

`sidecar-session-01`, `sidecar-pull-01` and `sidecar-expired-01` run on `boards-lane.sh` (`run-all.sh` runs them). `fake-sidecar.mjs` logs every request with its body to `data/verify/app/fake-sidecar.log`. ## Gotchas

- The lane runs Electron with `--use-mock-keychain`, so the seal there never touches the login Keychain. The real-Keychain proof is `keychain-lane.sh`: it bundles `src/server/secrets/store.ts` into an Electron main named `lead-studio-lane-<pid>`, migrates a legacy row on a throwaway DB in the gitignored verify data folder, checks the `.dump` holds no plaintext, and deletes the `lead-studio-lane-<pid> Safe Storage` item on exit. It refuses to run if that item already exists.
- The seed writes the Graph token as a legacy `secrets` row on purpose: the journey proves the boot migration moves it.
- Running `umami-01` before `own-01` on the same lane makes `own-01` fail: the pull replaces the seed's 18 OWN01 visits with 4.

## Card state across a restart

`card-state-lane.sh` starts `fake-sidecar.mjs`, seeds the app and runs `card-state-01`, then copies the lane DB with `sqlite3 .backup` to `data/verify/app/restart.db`, quits the app (`app-down.sh`), and reopens a new app on that copy (`APP_REAL_DB=... app-up.sh --real`) for `card-state-02`. `run-all.sh` runs it as its own lane. `card-state-01` prints `ok: Settings > Sources: no card names a next pull time; only the sidecar card has a Pull button`, `ok: the sidecar's session expires and a pull fails: the card shows Error with its reason`, `ok: the session is back and Test connection passes: the failed pull still shows Error, a check proves the key and not the data` (one pill, the DB row `pull_state` `error`, no `check_message`, `checked_at` after `pulled_at`), `ok: a pull succeeds: the card shows only Ready, no Error and no Verified`, `ok: a pull fails again, leaving Error as the newest event for the restart`, and saves `card-state-01-error.png` and `card-state-01-ready.png`. `card-state-02` prints `ok: after the restart the sidecar card still shows the last pull's Error and its reason` and `ok: no check or pull ran on start: connector_status holds the same one row per event`, and saves `card-state-02-after-restart.png`. The fake sidecar answers `/health` as the real one does (logged in, no Instagram call). The sidecar card's Test connection also pulls `/profile`, so it fails while the session is set to expired. `POST /__medias?state=empty` makes it answer `/medias` with an empty last page, so `card-state-01`'s good pull completes; `state=refuse` restores the 503.
