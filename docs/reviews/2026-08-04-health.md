## Findings

### HIGH

#### H1. A failed frame pass re-run destroys a good layout reading

`src/server/services/frame-pass.ts:126`

```ts
const cols = { layout: null, framesSampled: null, frameModel: null, framePassAt: now, framePassError: error };
```

`recordFramePassFailure` nulls `layout`, `framesSampled` and `frameModel` on both
branches, including the UPDATE branch at line 135 that runs when a `video_analyses` row
already exists. `frame-pass-runner.ts:138` `fail()` calls it on every failure path, so
`FRAME_EXTRACT_FAILED`, `FRAME_MODEL_FAILED`, `FRAME_PARSE_FAILED` and
`FRAME_VALIDATION_REJECTED` all reach it.

That path is reachable from the primary button. `layout-section.tsx:129` renders
"Re-run frame pass" whenever `layout !== null`, so the offered action on a video that
already has a good reading is precisely the one that can erase it.

Failure scenario: a video has a successful layout read from 12 frames. The user clicks
"Re-run frame pass". watch.py hits a transient ffmpeg error, or the Claude subprocess
times out at its 600s ceiling, or the model returns JSON that does not parse. `fail()`
runs, the UPDATE branch fires, and the layout column goes to null. The reading is gone.
There is no undo, and reproducing it costs another yt-dlp plus ffmpeg pass plus a
priced Claude subprocess run. It is the most expensive derived artifact in the product.

The existing test does not catch this. `frame-pass.test.ts:124` seeds a fresh video and
records a failure against it, which only exercises the INSERT branch. None of the seven
cases in `frame-pass-runner.test.ts` re-runs over an existing successful layout.

Fix: keep the null-out on the INSERT branch, where there is nothing to lose, and on the
UPDATE branch write only `framePassAt` and `framePassError`, leaving `layout`,
`framesSampled` and `frameModel` untouched.

```ts
if (existing) {
  await db.update(tables.videoAnalyses)
    .set({ framePassAt: now, framePassError: error })
    .where(eq(tables.videoAnalyses.videoId, videoId));
} else {
  await db.insert(tables.videoAnalyses).values({ videoId, createdAt: now, ...cols });
}
```

That needs one companion change in the UI, because `layout-section.tsx:83` computes
`failed` as `everRun && layout === null && !!framePassError`. Once a layout survives a
failure, that condition goes false and the user sees a stale reading with no sign the
re-run failed. Drop `layout === null` from the `failed` test and render the retained
reading and the error line together, so the section says what it knows and when it last
failed to improve on it. Add a test that runs a pass, succeeds, runs a second pass that
fails, and asserts the layout is still there.

#### H2. Frame pass resolves media paths outside the tested containment boundary

`src/server/services/frame-pass.ts:31`

```ts
const mediaRoot = process.env.MEDIA_ROOT ?? "data/media";
return { ok: true, path: path.resolve(mediaRoot, asset.storagePath) };
```

Two things are hand-rolled here that the codebase already owns.

The env read bypasses `src/server/config.ts:58`, which declares
`MEDIA_ROOT: z.string().min(1).default("data/media")`. The default string is duplicated,
so the two can drift, and the zod validation (min length 1) is skipped. `MEDIA_ROOT=""`
is rejected by config and accepted here.

More importantly the path join bypasses `resolveAssetPath` in
`src/server/media/store.ts:57`, which is the repo's own stated containment boundary
(store.ts:12 calls it a security boundary) and carries seven test cases for traversal,
absolute paths, NUL bytes, percent-encoding and the equal-to-root case
(`store.test.ts:31-78`). Every other consumer goes through it:
`src/app/api/media/[assetId]/route.ts:87` and `src/server/transcribe/index.ts:79`.
`frame-pass.ts` is the one call site that does not.

Failure scenario: a `media_assets.storage_path` holding `../../etc/something` resolves
to a path outside MEDIA_ROOT, and that path is handed to watch.py and then named to a
Claude subprocess that holds the `Read` tool. `resolveAssetPath` would have thrown
`MediaPathError` on it.

Fix: import `resolveAssetPath` and return `resolveAssetPath(asset.storagePath)`,
wrapping the `MediaPathError` into the existing `{ ok: false, reason }` shape so the
caller still gets a clean `FRAME_NO_VIDEO_ASSET`. Delete the local `mediaRoot` read.

Flagging the traversal severity itself as the Security reviewer's call. From a code
quality angle the finding stands on its own: one consumer out of three reimplements a
boundary the other two share.

### MEDIUM

#### M1. Log retention runs a full prune on every single insert

`src/server/logs/store.ts:86`

```ts
db.run(sql`delete from log_events where id <= (select max(id) - ${RETENTION_MAX} from log_events)`);
```

`RETENTION_MAX` is 50000 (line 30). Every call to `insertLogEvent` issues this DELETE
with its `select max(id)` subquery, whether the table holds 5 rows or 50000. Since
`insertLogEvent` is the single write path for backend, frontend and sidecar logs
(everything funnels through `POST /api/logs/ingest`), that doubles the statement count
on the busiest write path in the app.

This is the direct cause of the flaky test. `store.test.ts:130` inserts
`RETENTION_MAX + 5` rows, so the test alone issues about 100010 SQL statements. Alone it
finishes in roughly 1.5s. With 86 test files competing for CPU it crosses the 5000 ms
vitest default and fails, which is what happened on the first full run here.

Fix: amortize the prune instead of running it every time. A module-level counter that
fires the DELETE every 1000 inserts keeps the table bounded at 50000 plus at most 999
rows, which is well within the intent of a retention cap, and drops the statement count
on the hot path by three orders of magnitude. It also fixes the flake without touching
the test. If the test should be hardened independently, give that one case an explicit
timeout rather than raising the global one.

#### M2. `isUniqueViolation` exists three times, byte for byte

- `src/server/services/sync-engine.ts:182` (exported, and the only one with tests, at
  `sync-engine.test.ts:1772`)
- `src/server/media/store.ts:163` (private, identical body)
- `src/server/services/frame-pass-runner.ts:44` (private, identical body)

All three are the same four lines. The comment at `frame-pass-runner.ts:42` even names
the other two ("Same shape as `media/store.ts` and `sync-engine.ts#isUniqueViolation`"),
which documents the duplication rather than removing it.

Failure scenario: a drizzle upgrade or a driver swap changes the error shape. Someone
fixes `sync-engine.ts`, sees its test go green, and ships. The frame pass global lock at
`frame-pass-runner.ts:58` and the media asset dedupe at `store.ts:212` now rethrow
instead of recovering. For the frame pass that means the concurrent-pass path raises
instead of returning `FRAME_ALREADY_RUN`, and because `lock_key` is a constant, a row
left stuck at "running" is a global outage rather than a per-video one.

Fix: move it to a shared module, something like `src/server/db/errors.ts`, import it in
all three, and move the existing test cases there with it. Two of the three call sites
are currently protected by a test that does not import them.

#### M3. Two different components both exported as `ReachByPostBars`

- `src/components/mine/reach-by-post-bars.tsx:25`, props `{ posts: OwnPostRow[] }`
- `src/components/channels/outlier-history-chart.tsx:130`, props `{ videos: ChannelDetail["videos"] }`

Different data, different props, same name, and neither file name predicts which one you
get. `mine/page.tsx:5` imports it from a file named after it; `channels/[channelId]/page.tsx:8`
imports it from a file named `outlier-history-chart`, which is a second unrelated
component in the same module.

Failure scenario: someone autocompletes the import, picks the wrong module, and gets a
type error if they are lucky or a silently different chart if the shapes happen to line
up. Nothing here is broken today, but the naming buys nothing and costs a lookup every
time.

Fix: rename to what each one actually plots, `OwnReachByPostBars` and
`ChannelReachByPostBars`, and move the channels one into its own file next to the chart
module rather than sharing it.

#### M4. `npm run lint` is red on a clean checkout because vendor dirs are not ignored

`eslint.config.mjs:9`

`globalIgnores` lists only `.next/**`, `out/**`, `build/**` and `next-env.d.ts`. The
untracked `Crowsnest UI Mockups/` and `claude-animation/` directories sit in the lint
path, and they contribute 5 of the 9 errors and 16 of the 17 warnings, including three
hard parse errors on minified bundles:

```
claude-animation/confetti.effect.js

```

Failure scenario: a contributor clones, runs the lint script, sees a wall of errors in
files they did not write, and either learns to ignore lint output entirely or spends the
afternoon on a minified bundle. The four real `channel-card.tsx` errors are buried in
the noise.

Fix: add `"Crowsnest UI Mockups/**"` and `"claude-animation/**"` to the `globalIgnores`

pre-existing `channel-card.tsx` baseline visible enough to actually get fixed.

### LOW

#### L1. A non-object JSON envelope escapes the `ClaudeTaskError` contract

`src/server/services/claude-task.ts:66-74`

`envelope` is typed `Record<string, unknown>` but assigned straight from `JSON.parse`,
which is `any`, so TypeScript does not check it. Verified at runtime: if the CLI writes
`null` to stdout, `JSON.parse` succeeds and line 74 `envelope.is_error` throws
`TypeError: Cannot read properties of null (reading 'is_error')`. Every other failure in
this module is a `ClaudeTaskError`, so this one path breaks the module's own contract.
If stdout is a bare number, `envelope.is_error` is `undefined` and the function returns
`text: ""`, a successful-looking result with no content, which then surfaces downstream
as a confusing `FRAME_PARSE_FAILED` about missing JSON.

Impact is bounded: `frame-pass-runner.ts:92` catches everything from `ask`, so the user
sees a wrong error code and a confusing message rather than a crash.

Fix: after the parse, check the shape before reading fields.

```ts
if (envelope === null || typeof envelope !== "object" || Array.isArray(envelope)) {
  throw new ClaudeTaskError(`claude returned a non-object JSON envelope: ${stdout.trim().slice(0, 300)}`);
}
```

#### L2. Enrichment candidate order has no tiebreaker

`src/server/services/sync-engine.ts:687`

`.orderBy(desc(tables.videos.postedAt))` followed by `.limit(limit)`. SQLite does not
guarantee an order among rows with equal `postedAt`, so two runs over the same data can
pick a different set of reels once the cap bites. Instagram timestamps are second
resolution and a channel posting twice in the same second is not exotic.

Impact is small, since the pass is advisory and the next sync catches the other row. It
does make a "why did this reel not get enriched" question harder to answer than it
should be.

Fix: add `desc(tables.videos.externalId)` as a second sort key so the candidate set is
deterministic.

#### L3. `sync-engine.ts` is the one module that has outgrown its file

1788 lines, 44 top-level declarations, 6 exported functions plus a `__test` escape hatch
at line 1788, and a 2481-line test file beside it. It holds the lock, the page walk, the
retry policy, the cancel machinery, upsert, soft delete, view count enrichment, score
recompute and snapshots.

Marking this pre-existing and low rather than high on purpose. The internal quality is
genuinely good: the seams are already named (`acquireLock`, `createTracker`, `withRetry`,
`cancellableDelay`, `enrichViewCounts`, `softDeleteMissing`), the comments explain
decisions rather than restating code, and nothing in it reads as accidental. It is long
because the domain is, not because it is tangled.

If it gets split, the cheapest real cut is the retry and cancel machinery
(`retriesFor`, `backoffMs`, `cancellableDelay`, `withLiveness`, `sleepUnlessCancelled`,
`withRetry`, lines 467 to 656) into `sync-retry.ts`. That is about 190 lines with one
inbound dependency and no database access, and it would let the retry policy be tested
without standing up a sync.

## What was checked and came back clean

Worth recording, since a review that only lists problems misreads the codebase.

- **Type safety.** `tsc --noEmit` is clean across the whole repo. Zero errors.
- **Doc references in comments.** Every one of the 12 `docs/*.md` paths cited from
  `src/` resolves to a file that exists. The surface map asked whether the long
  design-rationale headers had drifted; on this axis they have not.
- **Comment-to-code ratio.** High (27 to 48 percent in the top 20 modules, topping out at
  `config.ts` and `sync-types.ts`), but the comments are load-bearing. Spot checks found
  them explaining why a decision was made rather than restating the line below. The
  comment at `sync-engine.ts:841` that records a wrong diagnosis being removed, and the
  one at `claude-task.ts:44` explaining why `--allowedTools` must be argv-last, are both
  the kind of thing that saves a future reader an hour. The one exception is
  `frame-pass-runner.ts:42`, which documents duplication instead of removing it (M2).
- **Test hygiene.** No `.skip`, no `.only`, no `test.todo` anywhere in the suite.
- **`enrichViewCounts`** (`sync-engine.ts:737`). Read in full. The two invariants the
  surface map flagged both hold: the heartbeat ticks once per reel, and both `tick` and
  `shouldStop` are caught inside the loop so neither can turn a successful page walk into
  `stopReason: "error"`. The `withheld` and `skipped` counters really are distinct, the
  three-consecutive-not-found stop is implemented as described, and the write path
  correctly refuses to store a null count. No findings.
- **`remix.ts`.** The surface map flagged it as a complexity target. It is 483 lines
  across 22 small functions with clear stage boundaries. No findings.
- **Frame pass anti-fabrication guard** (`frame-pass.ts:77-84`). Implemented as
  specified, covered by tests, and the runner keeps `FRAME_VALIDATION_REJECTED` distinct
  from `FRAME_PARSE_FAILED` so the one distinction the feature exists to make is visible
  in the error code.
- **Frame pass failure coverage.** `frame-pass-runner.test.ts` has seven cases covering
  extraction death, unusable JSON, missing video file, the validation rejection, the
  concurrent-lock path and the stuck-at-running path. The gap is the re-run-over-success
  case in H1.

## Recommendations by impact

1. **H1**, restrict `recordFramePassFailure` to the error columns on update. Silent loss
   of the most expensive artifact in the product, on the primary button, with no test.
2. **H2**, route frame pass media resolution through `resolveAssetPath`. Removes a
   duplicated default and puts the last consumer back inside a tested boundary.
3. **M1**, amortize the log retention prune. Fixes the suite flake and takes the double
   statement off every log write.
4. **M4**, add the two vendor globs to `globalIgnores`. One line, and it makes the lint
   signal usable again.
5. **M2**, hoist `isUniqueViolation` into a shared module and move the tests with it.
6. **M3**, rename the two `ReachByPostBars` components.
7. **L1**, **L2**, small correctness cleanups in the new frame pass and enrichment code.
8. **L3**, optional `sync-retry.ts` extraction, only if someone is already in that file.

Adding `knip` and `shellcheck` would light up the two skipped dimensions. `shellcheck`
is the better first buy: three shell scripts under `scripts/` are currently unchecked,
and one of them (`ig-service.sh`) is on the path a contributor runs first.
