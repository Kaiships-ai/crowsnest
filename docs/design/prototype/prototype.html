The hedge is the point. The stale-lock reaper waits 900 seconds before stealing the lock, so inside that window a run that looks stalled can still be alive. When the reaper fires it writes failed with SYNC_ABANDONED. Stalled takes red rather than amber, because amber would read as "still going".

crowsnest_sync_channel(handle | channelId, lookbackDays?) -> write { jobId, status, itemsSeen, itemsCreated, itemsUpdated, itemsFailed, stopReason } call { handle: "kallaway" } back { jobId: "sj_18", status: "running" }

Wraps runSync. Syncing is the one long action an agent wants before anything else. If one is running it returns "a sync is already running, job id X" and points at sync_status, rather than a unique index violation the model cannot read. v1 yes.

crowsnest_sync_status(jobId?) -> read { jobId, status, phase, channelsDone, channelsTotal, currentChannelHandle, retries, cancelRequested, gaps } call { } back { status: "running", phase: "pages", channelsDone: 1, channelsTotal: 1 }

Reads the sync_jobs progress row, already written at every page and channel boundary. Without it the agent blocks or guesses. v1 yes, sync_channel is unusable alone.

crowsnest_list_outliers(minScore, sinceDays, channelId, fleetId, sort, limit, offset) -> read { total, items: [{ videoId, channelHandle, caption, postedAt, viewCount, outlierScore, mediaType, url, hasTranscript, hasAnalysis }] } call { minScore: 3, limit: 5 } back { total: 1, items: [{ channelHandle: "kallaway", viewCount: 2272877, outlierScore: 10.1 }] }

Wraps getOutlierFeed, which already implements exactly these filters. The single most valuable tool on the list: it is the question the product exists to answer. v1 yes.

crowsnest_get_transcript(videoId, createIfMissing = false) -> read, or write when true { videoId, text, language, durationSec, source, createdAt } | { videoId, transcript: null, reason }

Reads the transcripts table. Without it the agent only sees captions. createIfMissing defaults to false because transcription is the heavy path and should be an explicit choice. v1 yes, read only.

crowsnest_analyze_post(videoId, force?) -> write { videoId, hookType, structureSegments, formatTags, styleTags, whyItWorked, model, createdAt }

Wraps getOrCreateAnalysis, which caches into video_analyses and returns the cached row when one exists, so a repeated call is cheap. That get or create shape is the right shape for an agent. v1 yes. Open: does this route to the local proxy or the real API. It is a text task by the stated rule, but analysis quality is what the product's value rests on.

crowsnest_generate_hooks(videoId | sessionId, count?, vaultItemId?) -> write { sessionId, hooks: string[] }

Wraps generateHooks, already grounded by the saved niche profile. v1 no, in my read. Generation is better in the UI where Kai can see the vault beside it, and the pane can drive the UI instead.

crowsnest_write_script(sessionId, chosenHook?, styleVaultItemId?, targetLengthSec?) -> write { sessionId, outline, variants: string[], scriptId }

Wraps the outline, variant and save path in remix.ts so a script produced in chat lands in the scripts table rather than only in the conversation. v1 no, same reason as hooks.

crowsnest_get_post(videoId) -> read { videoId, channel, caption, postedAt, mediaType, metrics, outlierScore, children, transcript, analysis }

Wraps getVideoDetail. The other tools return ids, so something has to turn an id into the full picture or every follow up needs three calls. v1 yes.

crowsnest_list_channels(fleetId?) -> read [{ channelId, handle, displayName, followerCount, mediaCount, lastSyncedAt, syncError }] back [{ handle: "kallaway", followerCount: 442447 }, { handle: "hormozi", lastSyncedAt: null }]

Wraps getChannelsList. The agent needs real handles to pass to the other tools, and guessing them fails. v1 yes, cheap and it unblocks the rest.

crowsnest_add_channel(handle, fleetId?) -> write { channelId, handle, created }

Wraps addChannel. Turns "track this creator" in chat into a real row. v1 no. Adding a channel is one click in the UI and a wrong handle costs a sync.

crowsnest_import_reel(url) -> write { videoId, channelId, created }

Wraps importReelByUrl. A single URL pasted into chat is the most common way research arrives, which is a real argument for it. v1 no, but it is the closest call on the tier 2 list.

crowsnest_search_vault(type?, query?) -> read [{ id, type, title, templateText, tags, sourceVideoId }]

Wraps getVaultItems. Without it the agent regenerates hooks that already exist in the vault. v1 no while the vault is nearly empty, yes the moment it is not.

crowsnest_own_channel_stats(sinceDays?) -> read, own identity only { measuredAt, account, posts: [{ postId, format, postedAt, reach, saves, shares, likes, comments, views, reachIndex }], medianReach, sampleSize } back { medianReach: 9, sampleSize: 8, account: { followers: 5, posts: 8 } }

Gated on G1 existing. Every field carries its sample size, because an agent summarizing this will otherwise report an 8 post average as a fact. v1 yes, the moment G1 ships.

crowsnest_compare_post(ownPostId, videoIds[]) -> read, both identities, never writes { mine: { unit: "reach", value: 14, median: 9, n: 8, index: 1.6 }, theirs: { unit: "views", value: 2272877, median: 224403, n: 8, index: 10.1 } }

Two explicitly separate halves, each with its own unit and its own denominator. This is the one analysis an agent cannot assemble from the other tools without re deriving both medians and probably mixing the units. v1 yes, it is the differentiator.

deliberately not exposed

No delete tool of any kind. Nothing touching Instagram credentials, sessions or login, because the two factor and challenge steps need a human in front of them. No publishing. No media bytes, assets are referenced by id. No settings writes: an agent that can change the niche profile silently changes every future generation.

Open. Separate stdio process or HTTP inside the running Next app. Separate is simpler to register and safe because the single flight sync lock is a partial unique index in the database rather than an in process mutex, which is what makes a second process safe at all. In process avoids a third process next to the dev server and the sidecar, but ties tool availability to the dev server being up, which is the thing Kai said he wanted to avoid. Also open: do write tools need an explicit confirmation argument, since the H3 permission prompt only exists inside the pane and a terminal session has its own permission model.
