### Behavior notes

- A fresh install (flag unset, no channels) is redirected to `/first-run` before any shell page renders. A database with a channel, or with the flag set, is never redirected, and `/first-run` sends a finished install to `/`.
- The rail shows four numbered steps: a passed step is clickable, the current one is marked, later ones are locked. "Skip setup for now" is available on every step and writes the flag.
- Focus saves the niche. Connect shows only the connected handle, and a wrong two factor or challenge code stays on the same field with an inline error. Channels commits the list on Continue and rejects a malformed handle inline at add time. First sync shows "Run first sync" until this step has launched a run, and "Open Crowsnest" appears on any terminal status.
- Settings' "Replay first run" clears the flag behind a confirm dialog and keeps all data.
- `kai kit init` needs a cached license, masks the Instagram password and Anthropic key, generates `IG_SERVICE_TOKEN` while it is the placeholder, writes `.env.local` at mode 0600, migrates, starts the app, and registers MCP.
- The Instagram username and password form validates against the live sidecar before saving. A rejected login saves nothing. A two factor or challenge result is saved only after the follow-up succeeds. The Anthropic key "Test" is a separate action from Save.
- With no key, AI features show a clear "add a key" state. With a key and an unreachable proxy, `getLlm()` calls Anthropic directly, and the dashboard badge uses the same live check.

## onboarding: test cases

Result markers: 🟢 pass, 🔴 bug, 🟡 blocked (missing dependency named in the cell). Rows still reading "not run" were not driven in QA round 1.

How to run these: onboarding spans a terminal half and an in-app half, so the setup differs by section. The terminal cases need a machine with the Kit installed and a cached license (`kai login` already run), on a real interactive terminal, a TTY, because the known defects only reproduce there, not under `kai kit init < answers`. The in-app cases need the dev server started, opened at `http://localhost:3001/first-run` (never `127.0.0.1`); to exercise the gate you need to control two facts, `app_settings.first_run_completed` and whether any `channels` row exists, and to reset between runs use Settings' "Replay first run", which clears the flag. The connect step needs the Instagram sidecar reachable (or deliberately down) and a set of real credentials that will accept, two factor, or challenge on demand. The Settings cases (sections 5 and 6 of [built features](#built-features)) need `/settings` opened, a valid and an invalid `ANTHROPIC_API_KEY` on hand, and, for the 9router rows, the `9router` binary installed but not running. The pure logic tests (`src/server/queries/first-run-gate.test.ts`, `src/components/first-run/onboarding-view.test.ts`, `src/components/status/dependency-status.test.ts`) and the server-action tests (`src/server/actions/ig-actions.test.ts`, `src/server/actions/settings-actions.test.ts`) run offline with `vitest`, no database and no browser, except where a case is marked `drizzle query`, which needs a temporary SQLite database. Browse-e2e cases are driven with the `browse` skill against the running dev server, per `references/browse-e2e-qa.md`; none of the `data-testid` values any journey below needs exist in the current markup yet, so every case in that lens is blocked on adding them first. Cases marked "build target, ENH-1" or "build target (see 03 §6)" assert the behavior [03-feature-description.md](#built-features) commits to but the code does not implement yet; they are the shape a future build should satisfy, not a fact yet true of the running app.
