# Mine

Mine is the user's own side of crowsnest: how their own Instagram account is doing and what they mean to post next. Its screen is Tuần này at `/`, the week planner. Own-channel numbers are measured from the official Instagram Graph API and stored for the MCP tools; no page lists them, and the Graph API card in Cài đặt is where the token is checked and a measurement started. The Graph API is a separate identity and code path from the sidecar that fills the feed.

## Data it holds

Schemas are in `src/server/db/schema.ts`. Mine owns these tables:

- `planned_posts`: a dated intention to publish. Stored `state` is `draft`, `scheduled`, `publishing`, `published`, or `failed`. `missed` is derived on read and never stored. The publish part also advances this row. Nullable `keyword` (the comment word viewers type to get the guide) and `magnet_url` (the guide link) are set over MCP by `crowsnest_set_plan_fields`.
- `plan_versions`: one proposed or approved reel list for a month (`YYYY-MM`) or ISO week (`YYYY-Www`). `version` counts up per period, `status` is `proposed`, `live`, or `superseded`, and `reels` is JSON checked by `ReelListSchema`. `planned_posts.planVersionId` and `planReelKey` link a draft to the version and reel that wrote it, and `planSynced` holds the reel fields that sync last wrote; all three stay null for plans made by hand or by remix.
- `own_account_snapshots`, `own_posts`, `own_post_insights`, `own_comments`, `own_account_breakdowns`: the own-channel set. `own_post_insights` is append-only, one row per post per measurement, so the latest row is the current numbers and all rows are the views over time. `own_account_breakdowns` is one generic table (metric, dimension, key, value) for the follower split and engaged-audience demographics.
- `app_settings` keys for stored fetch errors: `own_audience_fetch_error`, `own_follower_split_fetch_error`, `own_comments_fetch_error`, and `own_comments_fetched_at`.

It reads `channels` (the `isOwn` flag, at most one row, by the partial unique index `channels_single_own`) and `scripts` for plans. The own-channel tables hold no reference to `channels`; there is one Graph token, so one own account. `planned_posts.published_own_post_id` is plain text checked against `own_posts` in `markPlanPublishedAction`, not a foreign key. Secrets `IG_GRAPH_TOKEN` and `IG_GRAPH_USER_ID` come from Settings > API keys first, `.env.local` second.

## Boundaries

- Owns: the Tuần này week screen (`src/components/week/`), the Graph connect panel and publish dialog (`src/components/mine/`), the broken-token line (`src/components/status/graph-token-line.tsx`), the own-channel and planned-post queries (`src/server/queries/own-channel.ts`, `planned-posts.ts`), `planned-post-actions.ts` and `graph-actions.ts`, the Graph client (`src/server/graph/client.ts`) and token cache (`token-status.ts`), the measurement service and scheduler (`own-measure.ts`, `own-measure-scheduler.ts`), and the pure reel math (`reel-insights.ts`, `own-metrics.ts`).
- Called by: the landing page (`src/app/(shell)/(loaded)/page.tsx`, which renders Tuần này and redirects any `?tab=` to `/`), the Cài đặt page (mounts the connect panel), the publish part (advances `planned_posts`), and the MCP tool `crowsnest_metrics` (reads `getOwnChannelOverview` and `getOwnPosts`).
- Calls: `graph.instagram.com` (account, media, per-media insights, comments, account insights), the channels queries and `setOwnChannelAction`, the vault `getScripts` and `getVaultItems`, the `scoreMinUsablePosts` setting, and `server.ts`, which starts `startOwnMeasureScheduler()` beside the sync and publish schedulers.

## Invariants

- Own posts are read-only. `measureOwnChannel` (`src/server/services/own-measure.ts`) is the only writer of the own-channel tables, whether from "Measure now" (scope `all`) or the scheduler (scope `due`). The sidecar never touches them.
- One measurement at a time. A single-flight lock plus a call ledger live on `globalThis.__crowsnestOwnMeasure`, because the tsx `server.ts` and the Next bundle load separate module copies. A `due` run that finds the lock held returns `MEASURE_BUSY`; an `all` run waits.
- Graph budget: 200 calls per hour per user. A scheduled run uses at most 150, "Measure now" at most 190, each cut to 200 minus the calls made in the last hour minus 10 (`OWN_MEASURE_CALL_BUDGET`, `OWN_MEASURE_MANUAL_CALL_BUDGET`). The client transport counts every call, so publishes and token checks count too. A rate limit stops the run; rows already written stay. The ledger is in memory and resets on restart.
- Due-ness is derived from `own_post_insights`, never stored. A reel under 72 hours old is due when its newest successful capture is an hour old, older posts at 24 hours, each with five minutes of slack. Failures back off from the newest failure: a day for a non-transient `invalid_request`, an hour for a young post, and for an older post one retry an hour later then daily.
- The read picks each post's newest successful insight row, falling back to the newest failed row only when none succeeded (`getPostsWithLatestInsights`), so a later failed capture never hides the last good numbers.
- A metric the API does not return is null, never zero. Per-viewer rates are null when `reach` is missing or zero. Bio link taps read 0 on a successful call without the action and null only on a failed call.
- The reel metric set leaves out `follows` and `profile_visits` (Meta reports them for feed and story media only). A failed extended call retries once with the core set, except on auth or rate-limit failures. A permission refusal (HTTP code 200 to 299, or code 10 naming a permission) ends the run with `GRAPH_PERMISSION_DENIED`.
- Every own-channel metric carries `sampleSize` and `failedSampleSize` (rendered "n of N measured"), and no tile shows until a real Graph call returned the metric (`src/server/queries/own-channel.ts`).
- `total_watch_time_ms` is stored although no block shows it, because a past snapshot cannot be re-fetched.
- Account breakdowns run only when no run was cut short, 4 calls of budget remain, and the newest stored batch is 24 hours old (`breakdownsStale`).
- The scheduler ticks hourly (override `OWN_MEASURE_SCHEDULER_INTERVAL_MS`) and 30 seconds after boot. It skips a tick with no own channel, no configured token, or the lock held (`own-measure-scheduler.ts`).
- Failures are classified by HTTP status and code, never by error `type`, because Meta sends `OAuthException` on nearly every error (`src/server/graph/client.ts`, tested in `client.test.ts`).
- The broken-token line (`graph-token-line.tsx`, `graph-token-line` test id) shows on Tuần này and the Nguồn pages only for `auth_failed` or `permission_denied`, reading the cache with a timeout; a missing token, a rate limit, or a network blip shows nothing. It links to `/settings#graph-api`, and Check connection there refreshes the cache and clears it.
- Token status is cached on `globalThis.__crowsnestTokenStatus`: five minutes for definitive states, 30 seconds for transient ones. It is dropped when a token secret is saved or cleared and when a run ends in an auth failure. A remembered `permission_denied` stands over an `ok` live check until a measurement lands insights or the token changes.
- Planned posts: create and `savePlanEditAction` validate up front and write once; the edit is a single transaction. A date at save makes `scheduled`, none makes `draft`. A blank title is refused. A plan carrying a remix-session script cannot change that script in the dialog.
- A keyword belongs to at most one plan, compared case-insensitively for ASCII letters only: SQLite `lower()` folds A to Z, so `É` and `é` are two keywords. The partial unique index `planned_posts_keyword_lower` on `lower(keyword)` where it is not null enforces it, and `setPlanFieldsAction` maps that constraint to `KEYWORD_TAKEN` from a single UPDATE, so a refused call writes nothing. Null clears a field; a blank keyword is refused, not read as a clear. Keyword and guide link stay editable after a plan is scheduled or published.
- Plan versions (`src/server/services/plan-versions.ts`): the unique index `plan_versions_period_version` numbers versions per period and the partial unique index `plan_versions_single_live` allows at most one live version per period. Each reel carries a stable `key`; approve maps it to the period's draft with the same `planReelKey` and updates that draft instead of adding one. Approve runs in one transaction: it supersedes the old live version, marks this one live, deletes the period's pristine drafts whose key left the list, updates the other pristine drafts, and inserts drafts for reels with no post. A draft is pristine when it is in `draft` state, carries no script, video, caption, source video, or magnet URL, has no target length, video kind, or remix session (the calendar edit sets those without touching `planSynced`), and its title, date, time, keyword, and note still equal `planSynced`. Every other plan post is left untouched and returned under `kept` with its reel key, a reason (`not_draft`, `has_script`, `has_video`, `has_caption`, `has_source_video`, `has_magnet`, `has_settings`, `edited`), and `notApplied`, the reel fields the new version wanted but did not get (`removed` when the reel left the list). A plan-linked draft with a null `planSynced` is treated as `edited`, and its `notApplied` lists every reel field. A draft scheduled and then moved back to draft follows the same rule. Approving the live version again changes nothing, and approving an older superseded version makes it live the same way. Undo returns the live version to `proposed`, makes the most recently approved superseded version live, and syncs to it the same way; when no earlier live version exists it refuses with `NOTHING_TO_UNDO` and changes nothing, so a second undo either steps one further back or refuses. A reel keyword held by any other post, including a kept one, fails the whole approve with `KEYWORD_TAKEN`, and the error names the holder's post id and reel key; any other unique violation returns `PLAN_CONFLICT`. A week key `YYYY-W53` is refused for an ISO year with 52 weeks. Tuần này renders a list per day, so two reels on one day both show.
- Tuần này (`src/components/week/week-tab.tsx`, `week-screen.tsx`, pure rules in `week-model.ts`) is `/`; any `/?tab=` redirects to it. It reads the dated plans of the ISO week holding the server's local date, the week's plan versions (`listPlanVersions` with period `week`), and the latest funnel rows (`getFunnel`) for the week's keywords. Each day is a list, so two reels on one day both show. The five steps (idea, profile, video, publish, 48h numbers) count in order from plan fields: profile is a script or caption, video is an attached asset, publish is state `published` and not a dry run, numbers are any funnel row for the keyword. A dry-run publish reads "Đã đăng (dry run)", never plain published. The next-action chip picks, in day order, the first reel ready to publish, then a proposed plan draft newer than the live version, then a failed publish, then a reel that needs a video, then a reel that needs a profile ("Viết hồ sơ"). With none of those it shows "Không có gì chờ anh" under its own test id. Moves follow one guarded server action, `movePlannedPostAction`, used by the drop, the day select, and their undo. It refuses a `published` or `publishing` row with `PLAN_LOCKED`, checking state inside the UPDATE so a stale tab cannot win. It never changes `state`: a failed reel stays failed with its `lastError` (retry stays an explicit action), a draft stays a draft. When the row has a `scheduledAt`, the move carries it to the new day at the same local time and rewrites `idempotencyKey`; it refuses a past day (`PLAN_MOVE_TO_PAST`) and never writes a past `scheduledAt` onto a scheduled row (`PLAN_SCHEDULE_IN_PAST`). It returns the prior date, time, and `scheduledAt`, and undo passes that snapshot back as `{ restore }` to the same action. Past days are not drop targets and are not offered in the select. The UI moves the reel at once and keeps a sequence number per reel, so only the newest answer for that reel can roll the UI back. The hook field edits the linked remix session's `chosen_hook` through `updateStageAction`; a plan with no `remixSessionId` (or whose session is gone) shows an empty hook step with one "Mở remix" link instead. Hook templates from the vault (`getVaultItems("hook")`) fill the hook in one press: `{topic}` and `{keyword}` take the session topic, else the reel keyword. A hook with any other `{...}` slot stays in the input and is never saved until the slot is filled. The plan `note` is its own field, saved on blur and on closing the drawer (Esc or overlay). The drawer's "Chuyển sang ngày" select is the keyboard path for a move and runs the same optimistic save and undo as a drop. A plan whose `sourceVideoId` points at a video with `deletedAt` set shows a red "Video gốc đã bị xoá khỏi Instagram" line. The newest sync run streams over `useRunStream`: a progress line while it runs, a failed run links to its run detail. Approve calls `approvePlanVersionAction`. The toast offers undo only when an earlier live version exists, and undo passes the approved version id to `undoPlanVersionAction`, which refuses with `LIVE_CHANGED` if another version went live since. The publish confirm reads as a dry run when the env or the row's `dryRun` says so. Publish asks inline before `publishNowAction`; video and caption go through the existing `PublishDialog`. A funnel metric with no row shows "chưa đo", never 0. The drop records `week-drop-paint` and `week-drop-store` performance measures.
- `measureOwnChannelAction` never throws; it returns `MEASURE_FAILED` for a non-Graph error and revalidates `/` either way. `setOwnChannelAction` and `unsetOwnChannelAction` exist in `channel-actions.ts`, but no screen calls them.
- Live Graph metric names and units (`reposts`, `reels_skip_rate`, the account `views` split, watch time in milliseconds) and the throttle codes come from Meta's documentation, not a live response, because the configured token is rejected.
