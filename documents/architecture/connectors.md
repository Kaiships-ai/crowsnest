# Connectors

A connector is one outside source crowsnest reads from: Instagram Graph, the instagrapi sidecar, Umami, Polar, and later ChatbotX. Each is a manifest (what it is, as data) plus an adapter (the code that talks to it). The connector also owns the secrets the source needs, and those secrets are sealed by the macOS Keychain.

## Data it holds

- A manifest per connector (`ConnectorManifest` in `src/server/connectors/types.ts`): `id` (its folder name), `label`, `auth` (`oauth`, `api-key`, `browser-session`, `cli` or `mcp`), `secrets` (name, label, `perAccount`, `optional`) and `feeds`, the ledger counts it fills (`CountId` from `src/server/metrics/ledger.ts`).
- An adapter or `null` (`ConnectorAdapter`): `testConnection()` never throws; `sample()`, when present, is Test connection: one real read that returns a `Sample`, a line to show (`{ ok: true, line }`) or the sentence that says what to do and the source's retry time (`{ ok: false, message, retryAfter }`); `pull()` returns a `PullResult` (`src/server/lib/pull-result.ts`). `null` is a manifest-only connector: listed with status `not-connected`, never called.
- `sealed_secrets`: `name`, `sealed`, `updated_at`. `sealed` is base64 ciphertext from Orca's `SecretStore` (`src/shared/secret-store.ts`, Electron safeStorage), whose key lives in the login Keychain as the app's Safe Storage item. A per-account Instagram password is keyed `IG_PASSWORD::<accountId>`.
- `secrets`: the legacy plaintext table. Nothing writes to it; the boot migration drains it.
- `umami_days`: one row per Asia/Ho_Chi_Minh day that a complete Umami pull counted: `raw` and `clean` counts (visitors, pageviews, custom events, paths, utm query strings, and per `utm_campaign` the pageviews, gift-page visits, `gift_signup`, `checkout_click` and `purchase`), `test_sessions_dropped`, `final` (1 once a pull ran after the day ended) and `fetched_at`. `clean` drops every session that touched a test marker, as `ksa_sync.py` does: a `utm_campaign` with a whole-token `test`, `utm_source=verify`, or a `/__test-purchase` or `/__diag` path.

## Boundaries

- Owns: `src/server/connectors/` (types, `registry.ts`, `secrets.ts`, one folder per connector) and `src/server/secrets/store.ts`.
- Called by: the Graph client, the sidecar client and launcher, IG accounts, the Settings secret actions, the engine bridge (`listConnectors`, `testConnector`, `sampleConnector`, `pullConnector`, `getVaultBoard`, `setConnectorSecret`, `startSidecarAction`, `stopSidecarAction`, `testSidecarSessionAction`, `testGraphTokenAction`, `saveGraphTokenAction`, `startGraphPullAction`, `stopGraphPullAction`, `testPolarTokenAction`, `savePolarTokenAction`, `getPolarOrganization`, error scrubbing), `src/server/services/connector-status.ts`, the `kai` CLI, and boot (`startInApp` in `src/server/start.ts` runs the migration).
- Calls: the source's own client through the adapter, and `SecretStore` for sealing.

## Invariants

- **Adding a connector is new files in one folder.** `registry.ts` finds `./*/index.ts` with `import.meta.glob`; there is no list to edit. A folder whose manifest id is not its folder name, or a secret two connectors declare, throws on boot. `registry.test.ts` checks the folders on disk against the registry and registers a sample connector from `__fixtures__/sample-crm/` with no core edit.
- **The engine reads a secret only through a manifest.** `readSecret(manifest, name)` in `connectors/secrets.ts` takes only a name the manifest declares. Only `connectors/secrets.ts` and `src/server/start.ts` import the keychain store; `registry.test.ts` fails on any other importer. The glob stays in `registry.ts`, so tsx scripts that read secrets never load it.
- **No secret value crosses the bridge.** `listConnectors` and `getSecretStatusAction` return status and source (`keychain`, `db`, `env`, `none`), never a value. The bridge calls that write a secret are `setConnectorSecret(connectorId, field, value)` and `saveSidecarSessionAction(sessionid)`, which saves `IG_SESSIONID` through it and then records the sample. `setConnectorSecret` is in `src/server/actions/secrets-actions.ts`. It refuses a connector or a field the manifest does not declare and a blank value, seals the value with `writeSecret`, and returns only `{ ok }` or `{ ok: false, error }`. It accepts a manifest-only connector, so a key can be saved before its adapter exists. For `ig-sidecar` `IG_SESSIONID` it calls `igLoginBySessionAction` (`src/server/actions/ig-actions.ts`), which saves the id and has the sidecar adopt it (`POST /login-by-session`); a refused id or a sidecar that cannot be reached returns `ok: false` with the reason, which the Sources dialog shows. `engine-calls.test.ts` saves a sentinel value and checks that no bridge read returns it.
- **A secret is stored sealed or not at all.** `setSecret` seals, reads the row back and unseals it, and only then drops a legacy row of the same name, in one transaction. When the Keychain cannot seal, it throws and nothing changes.
- **The boot migration keeps what it cannot move.** `migrateSecretsToKeychain` moves each legacy row; a failed seal or read-back leaves that row and is logged as `secrets.keychain_move_failed`. A rerun after a clean pass is a no-op.
- **Read order:** sealed value, then a legacy row not yet moved, then the env var of the same name. `IG_PROXY` and `IG_DEVICE_SEED` stay env only.
- **Outside Electron there is no Keychain.** A tsx script or the `kai` CLI has no `SecretStore`. It reads a legacy row the app has not migrated yet, or the env var. A secret the app has already sealed throws `SecretLockedError`, which says to run from Lead Studio or set the env var, unless the env var is set. A write throws, and `getOrCreateServiceToken` with no token says to open Lead Studio once or set `IG_SERVICE_TOKEN`.
- **A secret is sealed only when the store reports no protection gap.** If `describeProtectionGap()` names a gap, `setSecret` throws and the migration keeps the legacy row and reports it.

- **An Umami pull stores only a complete pull.** `pullUmami` (`src/server/connectors/umami/pull.ts`) sends the API key as `Authorization: Bearer <key>` on every call (Umami refuses it as `x-umami-api-key`) and reads `/api/websites/:id/events` page by page from the oldest day that is not final, or on the first pull from the oldest plan with a keyword (at most a year back), to now. It also reads the day before that first day, which is never counted: it only seeds each session's campaign, so a session that came with a campaign before midnight keeps it after. Paging stops once `count` events came back, or at the first empty page when an answer leaves `count` out. Each page reports `page x / N` (N from `count` and the answer's `pageSize`) through `onPage`, and a Stop (`shouldStop`) is checked before each page after the first, so the page in hand finishes and the pull ends `partial` with reason "you stopped the pull". Past 400 pages (`MAX_PAGES`) the pull stops as `partial` and writes nothing. A session belongs to the first `utm_campaign` it carried anywhere in the pull, not per day (`countDays` in `days.ts`). Only when every page came back does it write, in one transaction, each day's counts to `umami_days` and three `reel_funnel` rows per plan keyword (`source` `umami`, `agent` `umami`): `visits`, the clean pageviews of a `/get/` page in sessions whose first `utm_campaign` is the keyword (case-insensitive), `emails`, their `gift_signup` events, and `checkouts`, their `checkout_click` events, each summed over every stored day. Both are counts, so they add across days and keywords. A 401 is "Umami rejected the key (401). Create a new key and paste it." (C13), a refused connection "Cannot reach <host>. Check that your Umami server is up, then try again.", and no answer in 30 s "<host> did not answer within 30 seconds." A failed page after the first is `partial` and a failed first page is `failed`; either writes nothing, so the boards keep the last complete numbers, the Sources card reads Partial or Error, and every number from that source is marked where it shows.
- **Umami finds its website through teams.** `listUmamiWebsites` reads `/api/websites` and `/api/teams`, then `/api/teams/:id/websites` for each team, and merges them by id: an admin's own list can be empty while a team holds the site. The key dialog's Test connection (`testUmamiKeyAction`) lists them and saves nothing. Save (`saveUmamiKeyAction`) tests again, stores `UMAMI_URL` (an address typed without a scheme gets `https://`), `UMAMI_API_KEY` and the picked `UMAMI_WEBSITE_ID`, clears an older build's `UMAMI_USERNAME` and `UMAMI_PASSWORD`, and records the sample line (`<domain> · <host>`). An older build's saved `UMAMI_URL` stays and fills the dialog (`umamiAddressAction`).
- **Nothing pulls on a schedule.** The app runs on the operator's Mac, so a pull runs only when something asks for one: the bridge's `pullConnector`, which agents and the verify journeys call, the sidecar card's Pull rivals, the Graph card's Pull my channel, the Umami card's Pull funnel, or a sync or measurement the operator or an agent starts. No check or pull runs on start. Only the publish scheduler runs on a timer, and only with `LEAD_STUDIO_PUBLISH_JOBS=1`.
- **A card shows a failed check, else the last pull.** `connector_status` holds one row per connector: the last pull's outcome (`pull_state`, `ready`, `pulling`, `partial` or `error` under a CHECK constraint, `pull_message`, one sentence that says what is wrong and what to do, `pull_detail`, the raw reason, and `pulled_at`), the last check's `check_message` (null when it passed) and `checked_at`, `off_at` (set while the sidecar is switched off), `updated_at` (also a pull's heartbeat), and for a pull `progress_done`, `progress_total`, `progress_label` (the rival in hand), `started_at`, `retry_after` (no pull or test before it, from the source's own wait) and `summary` (JSON `ConnectorSummary`: the last passing sample's line and the last pull's `PullSummary`: total, done, updated, new items, failed, duration, how it stopped, and each item's result). Its writers are `recordCheck`, `recordPull` and the pull, sample and switch writers below, all in `src/server/services/connector-status.ts`. Each upserts only its own columns, so a pull's outcome stays until the next pull and the state survives a restart. `cardStatus` derives the card's one state: `off`, then `pulling`, then a check error, then a pull error, then a pull partial, else `ready`. A passing check proves the key and not the data, so it never hides a failed or partial pull. A complete pull proves the key as well, so it also clears a check's error. The bridge's `testConnector` runs `checkConnector` and `pullConnector` runs the adapter's pull, and both record through it. A board refresh records too: `startSyncAction` records a full sync (the card pull) on `ig-sidecar` (a sync scoped to some channels is not the connector's pull and records nothing) and `measureOwnChannelAction` its measurement on `instagram-graph`, through the same mappings the adapters use (`syncPull`, `measurePull`). A `complete` pull is `ready`, a `partial` pull is `partial` with `missing <what>: <reason>` as the detail, and a `failed` or thrown pull is `error` with the reason as the detail. `pullConnector` refuses a connector with no `pull` or one that is not set up, and rethrows `SyncAlreadyRunningError` when a sync already runs; it records nothing then. A pull only reads from its source.
- **A pull in flight is a row, and a lost pull reads Partial.** `recordPullStart` sets `pull_state` to `pulling` and writes the starting pull's summary first: a fresh pull starts a chain at its own start with no counts, and Pull the rest carries the chain's counts and `chainFrom`. `recordPullProgress` moves the done count, the label and `updated_at` (the heartbeat), and `recordPullEnd` records the outcome through `recordPull`, then the summary and `retry_after`. `readStatuses` reads a `pulling` row as `partial` with its done count when this process did not start that pull (the app quit or crashed mid-pull) or when its heartbeat is older than 10 minutes (`PULL_STALE_MS`), so no card stays stuck in Pulling. That Partial adds the done count to the summary its start wrote, so Pull the rest after a quit skips what the lost pull reached and its counts continue from there. The Graph card reads such a pull (`stop` `interrupted`) as "The pull stopped before it finished, at x/N.", as the sidecar card's Off mid-pull does. The rivals sync's lock is a `sync_jobs` row; `reapStaleLocks` in `sync-engine.ts` fails a `running` row whose heartbeat predates this process's start (`PROCESS_STARTED_AT`) as well as one silent for `LOCK_STALE_MS`, so the sidecar's Pull the rest after a relaunch never waits on the lost pull's lock. `readStatuses` writes nothing; `restFrom` and `recordPullStart` read the same settled row. `recordSample` records a Test connection: the check, plus the sample line on a pass or `retry_after` on a limit. `recordSwitch` sets `off_at` when the sidecar is switched off and clears it when it is switched on.
- **The card pull stops cleanly.** `startSyncAction()` with no channel ids is the sidecar card's pull: it runs `runSync` with `cardPull` and mirrors the engine's progress writes into `connector_status` (`onProgress`). In a card pull, Stop (`cancelSyncAction`) lets each rival in hand finish and starts no new one, so the run ends `partial` with the done count. The first rival that fails with `IG_RATE_LIMITED` (not retried), `IG_AUTH_REQUIRED` (an expired session) or `IG_SERVICE_DOWN` (a dead sidecar, after its one quick retry) ends the whole pull: no rival after it starts. A rival already in flight on another worker still finishes. The view-count enrichment pass, off unless `VIEW_COUNT_ENRICH_PER_CHANNEL` is set, catches its own errors per reel, so a limit there never ends the pull. A pull with an `IG_AUTH_REQUIRED` gap reads Error with the expired sentence (C7), even when some rivals finished first. `syncSummary` in `connectors/ig-sidecar/index.ts` turns the run into the summary: `stop` is `stopped`, `limited` (with `retry_after` from the sidecar's `retry_after_sec`) or `source-down`. Every other sync, scoped to channels or started by an agent, keeps the engine's usual cancel and retry rules.
- **The Graph card pull reports each post and stops between posts.** `startGraphPullAction` (`src/server/actions/graph-actions.ts`) records the pull start, runs `measureOwnChannel` with scope `all` and returns at once. `runMeasure` calls `onProgress` before each post with the done count, the posts in scope and the post's caption cut to 28 characters (`captionLabel`), and once after the last; the action writes each through `recordPullProgress`. It checks `shouldStop` before each post, so Stop (`stopGraphPullAction`) lets the post in hand finish and ends the run with `stoppedEarly: "stopped"`, skipping comments and breakdowns. A run that ends on the hour's budget or on Graph's rate limit carries `retryAfter`: the oldest Graph call in the last hour in `source_calls`, plus one hour (`hourFreesAt` in `src/server/lib/call-budget.ts`), since Graph sends no retry hint. `recordPullEnd` stores the summary (posts in scope, done, measured, failed, `stop` `stopped` or `limited`, and the follower count with its change since the snapshot before it) and that `retry_after`. Pull the rest sends `{ rest: true }`. `restFrom` in `src/server/services/connector-status.ts` returns the start of the last pull's chain (`chainFrom` in the summary, the first pull's start), and the run skips every post measured since then, so any number of stops in a row never measures a post twice and a failed post is tried again. `recordPullEnd` adds this pull's counts to the chain its start recorded, so the summary, the Partial lines and "Pull the rest (n)" count the whole channel. One card pull runs at a time; the action sets its Stop flag and clears it inside one try/finally, so a throw anywhere in the pull leaves Pull my channel working.

- **A Polar token is saved only after it passed Test connection.** `checkPolarToken` in `src/server/connectors/polar/index.ts` calls `GET /v1/organizations` on `https://api.polar.sh` (`POLAR_API_URL` overrides it only in a dev or verify app; the packaged Kit ignores it) with the token as a Bearer, 10 s timeout. A 200 with an organization passes with the first one's name; a 401 reads "Polar rejected the token (401). Create a new organization token and paste it."; no answer reads "Cannot reach Polar. Check your internet connection, then test again."; another status names it; a 200 with no organization says so. The bridge refuses a blank or whitespace-only token with "Enter a token.". `testPolarTokenAction(token)` in `polar/actions.ts` checks a draft and records nothing, so Cancel leaves the card as it was; it keeps the last passing draft in memory. `savePolarTokenAction(token)` refuses any token but that draft ("Test the token before you save it."), and does not call Polar: it seals the token, keeps the organization name in `app_settings` (`polar_organization`, not a secret) with a SHA-256 of the token that proved it (`polar_organization_token`), and records a passing check. `getPolarOrganization` returns the name only while the saved token matches that hash, so a token written any other way (`setConnectorSecret`, the environment) never shows it. The card's Test connection is `testConnector("polar")`: it checks the saved token, records the outcome, on a pass refreshes the kept name, and on any failure (no token, 401, unreachable) clears it. Nothing tests on paste or on save.

## Settings > Sources

`LeadSourcesPane` in `src/renderer/src/components/settings/LeadSourcesPane.tsx` is the Sources pane in Settings (id `lead-sources`, group Set Up), laid out like Orca's Integrations pane. It calls `getVaultBoard` (`src/server/queries/vault-board.ts`) and groups the connectors into Instagram and Funnel (a connector with no `SOURCE_INFO` entry lands in Funnel), each with a header and a one-line description. Each card is Orca's `IntegrationCardShell`: icon, name, one line on what the source gives, and the status pill in Orca's tones (`SOURCE_STATE`): `ready` reads Ready, `partial` Partial, `error` Error, `not-connected` Not configured, `off` Off, `pulling` Pulling. While a Re-check call is pending, the card alone reads Checking; that state lives in the renderer and is never stored.

- One primary action: Connect when not configured, else Edit key. Both open `SourceKeyDialog` (`LeadSourceKeyDialog.tsx`), shaped like Orca's Linear key dialog: one password field per secret the manifest declares, saved with `setConnectorSecret`. No value is ever read back; a saved secret shows "Saved · paste to replace".
- The body is the row's `message` when there is one, else a plain line for the state. The raw `detail` sits under it, small, never as the headline. A connected card shows the last pull time and, for `instagram-graph`, the Graph calls left in the rolling hour. No card names a next pull, since none is scheduled.
- Learn more (when the source has public docs) and Re-check (`testConnector`). These cards have no Pull button. Re-check reloads the board when the call ends, so the pill shows the event just recorded and no separate check badge exists. A bridge call that fails before reaching the connector records nothing and shows its error in the detail line.

The Instagram sidecar has its own card, `SidecarSourceCard` (`sidecar-source-card.tsx`), built to the approved connector prototype. It derives one view from the row, the sidecar's `/health` (`getIgStatusAction`) and its own pending work: Off, Starting, Not connected, the session id form, Testing, Ready (sample and last rivals pull), Pulling, the summary, Stopped, Limited (the limited rival with one row either side, Pull the rest off until `retry_after`), a limited test, Error, and Off mid-pull. The switch starts and stops the sidecar through the bridge's `startSidecarAction` and `stopSidecarAction`. Both act only on the local process, so they sit on the bridge, while the Instagram login actions stay off it. Turning it on keeps the card in Starting while the spawned process is alive and polls `/health` for up to 60 s, since a fresh install's first `uv run` builds the venv (7 s with an empty uv cache, 18 s when uv also downloads Python). It fails at once when the process exits, and at 60 s it stops the process and fails. `startSidecar` (`src/server/sidecar/control.ts`) clears `data/sidecar.pid` before it spawns, so a failed spawn leaves no old pid to poll or kill. The spawn is detached, so `stopSidecar` signals the whole process group (`kill -pid`), and `uv`'s python child never outlives it; on Windows, which has no process groups, it runs `taskkill /T`. Test connection replaces Re-check. Not connected also has "How to get a session id", which opens the session id form; the form's hint names the steps ("Open instagram.com › DevTools › Application › Cookies › sessionid."). The session id form tests only when Test connection is pressed and turns Save on only after a pass. Test connection (`testSidecarSessionAction`) sends the pasted id to the sidecar's `POST /sample-session`, which tries it on a throwaway client and returns its own profile; nothing is saved or adopted. Save (`saveSidecarSessionAction`) stores the id, has the sidecar adopt it (`POST /login-by-session`) and records the sample. A stored and adopted id is a saved session: the form closes even when the sample after it fails, and the card shows that sample's error (an Instagram limit reads the limited test, C8). Only a refused id keeps the form open with the refusal. Cancel discards the id, so the old session keeps working. Stop cancels by the job id `startSyncAction` returned, so it works before the first progress poll. While the row is `pulling` the card polls `getSyncProgressAction` once a second and renders `SourcePullProgress` from `source-pull-progress.tsx` (the rival in hand, x of N, the elapsed time, Stop, and a long-pull note after 2 minutes); `SourcePullSummary` renders the summary. Both are shared, and the Graph card reuses them. The Partial headline (stopped, limited, failed rivals, off mid-pull) is `status-warning`; in the limited rival's window, ✓ is `status-success` and ! is `destructive`. Pull the rest sends `{ rest: true }` to `startSyncAction`, which skips rivals updated since the last pull's chain began (`restFrom`, as on the Graph card) and adds the chain's counts, so x of N and Pull the rest count all rivals however many times the pull stopped. A card pull also refreshes your own channel, after the rivals, but x of N, the summary and Pull the rest count and list rivals only; a failed own-channel pull is logged (`sync.own_channel.failed`) and changes nothing on the card.

The Instagram Graph API has its own card too, `GraphSourceCard` (`graph-source-card.tsx`), built to the prototype's Graph frames: Not connected (Enter token, How to get a token), the token form, Testing, Ready (`@handle` from the last test, and the last pull's time, posts and calls left of 200 this hour), Pulling, the summary (Posts measured, Followers with the change, Calls left this hour), Stopped, Limited (C11), Partial and Error. The token form is `SourceKeyForm` (`source-key-form.tsx`), shared with the sidecar's session id form: Test connection (`testGraphTokenAction`) calls `/me` with the pasted token through `tokenAccount` in the Graph client and shows "✓ Token works · @handle · id N" (C9); nothing is saved, and a refused token shows "Instagram rejected this token. Copy a new one and paste it again." with Save off. Save (`saveGraphTokenAction`) calls `/me` again, stores the token and the user id it returned, and records the sample. Test connection on the card is `sampleConnector`. While the row is `pulling` the card reloads the board once a second and renders `SourcePullProgress` with "Pulling post 'caption'", x / N posts, ✓ measured and the calls left this hour; Stop reads "Stopping after this post…". Limited reads "Pulled x/N posts. The 200 calls for this hour are used up." with "Pull the rest (n) · after HH:MM" off until `retry_after`. A pull's Error keeps Change token and Test connection; once a later test passes, it offers Pull my channel instead of Change token as the first button, since a passing check never clears a pull's error. No read-only Graph call returns the token's expiry for an Instagram Login token, so the card shows no days-left line.

The Polar card is its own component, `PolarSourceCard` in `polar-source-card.tsx`, built to the approved prototype's Polar states. It has no Key dialog and no Pull button. Not connected shows "Enter access token" and a token help link. The token form sits inside the card: a password field, the help link, Cancel, Test connection (on once a token is typed) and Save (on only after a passing test, with "Save turns on after a passing test." until then). Test connection shows Testing, then "✓ Token works · organization <name>" or the error, both inside the form. Ready shows "Organization <name> · tested HH:MM" from `getPolarOrganization` and the row's `checked_at`, "Pulling orders comes in a later release.", and Test connection and Change token. While the card's test runs, the pill reads Testing with a spinner (`statusBusy`). Error shows the check's message with Change token and Test connection.

The Umami card, `UmamiSourceCard` (`umami-source-card.tsx`), follows the same prototype: Not connected, the dialog (`UmamiKeyForm` in `umami-key-form.tsx`: address and API key; nothing tests on typing; Test connection names the one website and picks it, or shows a Website picker for several; a 401 or an unreachable address shows inside the dialog; Save turns on only after a passing test and a pick), Testing, Ready (`Website <domain> · <host>` and the last pull), Pulling (`startUmamiPullAction`; `SourcePullProgress` with `page x / N`, Stop through `stopUmamiPullAction`, the long-pull note after 2 minutes), the summary (headed with the window the pull covered, `PullSummary.window` such as "last 30 days"; gift page visits, email signups and checkout clicks from `getFunnelTotals` in `services/funnel.ts`, the per-keyword sums the Funnel board adds up, and Open Funnel board), Stopped and Partial ("Nothing new was stored", with the time of the numbers the funnel keeps), Error (C13, Change API key) and Unreachable (Pull funnel, Change address). Unreachable is the error whose summary has `down`: `getJson` throws a `SourceDownError` (`src/server/lib/pull-result.ts`) when nothing answers on the address, the sample passes it on as `down`, a failed pull keeps it as its reason, and `recordSample` and `recordPullEnd` write it to the summary; the card never reads the message text. Save (`saveUmamiKeyAction`) trims the key, tests it again, then writes `UMAMI_URL`, `UMAMI_API_KEY` and `UMAMI_WEBSITE_ID` and deletes `UMAMI_USERNAME` and `UMAMI_PASSWORD` in one transaction (`writeSecrets` in `src/server/connectors/secrets.ts`), so a failed write keeps every old value. The card polls `getVaultBoard` once a second while the row is `pulling`. When a pull ends complete, and when Open Funnel board is pressed, the card calls `notifyFunnelChanged` (`src/renderer/src/lib/funnel-changed.ts`), and a mounted `FunnelBoard` loads again, so an open Funnel tab never keeps the numbers from before the pull. An empty events page before Umami's `count` is reached makes the pull partial, not complete.

`getVaultBoard` decides `state`, one of `not-connected | off | pulling | ready | partial | error`: status not `configured` is `not-connected`; otherwise `cardStatus` of its `connector_status` row, which is `ready` when the connector has no row yet. It also passes on the pull's `progress`, `retry_after` and parsed `summary`. The sidebar's Sources row and every "not connected" badge on a board open this pane (`openLeadSourcesSettings`).
