# Crowsnest v0.3 gap analysis and slice plan

Product thesis for v0.3: Crowsnest is the data and action brain reached over MCP; Claude,
Codex, or another external agent is the reasoning brain. The core content workflow must
not depend on an internal Anthropic API key. This document is the fact-based audit that
opens the v0.3 work, with file and line evidence, and the slice plan that follows from it.

## What already works

- Install and lifecycle. `packaging/install.sh.template` does a keyed `curl | sh` install
  under `~/.kai` with checksum verification, atomic extraction, offline python venv, and
  version flip with rollback. `src/cli/kai.ts` gives `login`, `kit init`, `up`, `start`,
  `stop`, `status`, `doctor`, `update`, `rollback`. License is Polar-backed
  (`src/cli/license.ts`), cached at `~/.kai/state/entitlement.json`, entered once.
- MCP surface. `src/server/mcp/mcp-server.ts` exposes 27 tools. The remix chain is already
  keyless: `crowsnest_remix_hooks/outline/variants` return a prompt and the agent writes
  the result (P0 slice 2b). `crowsnest_save_analysis` is a keyless, agent-authored write
  stamped `source: "mcp"`.
- One data contract. The app UI and MCP both read `src/server/queries/*` and mutate through
  `src/server/actions/*`. There is no second data path.
- shadcn migration is about 95 percent done: the style is flipped to `base-nova`, 18 `ui/*`
  wrappers are on `@base-ui/react`, and only `src/components/ui/form.tsx` plus the
  `radix-ui` dependency remain.

## Gaps by definition-of-done area

### 1. Buyer install and MCP

The one real gap was MCP registration: the app hosts `/api/mcp`, but nothing registered it
with Claude, Codex, or a generic client, and `kai doctor` never checked it. Closed in this
branch by `kai mcp` and a doctor check (see `src/cli/mcp-register.ts`, `src/cli/kai.ts`).

### 2. MCP-first content machine (largest product gap)

The read side is complete; the agent-authored write side is not. Only `save_analysis`
persists. The rest of the flow has read tools but no keyless persistence:

| Artifact | Save tool today | Data model today | Evidence |
| --- | --- | --- | --- |
| Angles | none | none (`angle` is only a per-idea column) | `schema.ts:324` |
| Outlier library | read-only compute | none | `queries/research.ts:54,71` |
| Ideas (100+) | none (only internal-LLM `generateIdea`) | `idea` table, unique index caps one idea per source video | `services/ideas.ts:74`, `schema.ts:332` |
| Week 01 to 04 plan | none (`crowsnest_plans` is read-only) | flat `plannedPosts`, no week or month grouping | `schema.ts:447` |
| Briefs | read-only compute | derived view, no table | `queries/post-brief.ts` |

Consequences: "generate 100+ ideas" is structurally impossible (one-per-video cap plus an
internal-key generator); there is no monthly-plan model; provenance exists only on analyses,
and even there `model` is left null. The weekly-plan skill wrote the plan to a markdown file, not the
DB. The remix skill referenced a tool that does not exist (`crowsnest_remix_regenerate_variant`)
and a stale `save_script` signature.

Internal-LLM callers still on the normal path: only ideas. `generateIdea`
(`services/ideas.ts:74`) is the sole generator and needs the key; there is no keyless idea
path through MCP. Remix generation via the internal model is dashboard-only and out of scope.

### 3. Multi-account sync

Single-account end to end: no account entity, flat `secrets(name, value)` slots
(`secrets/store.ts:14`), one sidecar and one PID file (`sidecar/control.ts:38`), one port
8765, one session file, one process-global `RLock` in the sidecar (`session.py:221`), one
cooldown file. The worker pool is parallel channels through the one account, which the code
itself flags as about 1.02x and rate-limit bound (`sync-engine.ts:1719`, `config.ts:47`).
No channel-to-account column. This is the largest and riskiest area, so v0.3 ships a minimal
honest slice, not the four-layer parallel rewrite, and documents the parallelism limit.

### 4. Dashboard and app UI

Not a rebuild. Finish the radix to base migration (`ui/form.tsx` plus drop the dep), then:
the dashboard is a KPI grid, not the content-machine workflow, and the per-screen primary
action slot in `components/layout/topbar.tsx:82` is empty. Fill the specific state gaps
(Channels whole-board empty state, Logs inline error). Most screens already have empty and
error states.

### 5. Docs, testing, release

Add buyer quickstart plus MCP setup, an MCP tool reference with example prompts, the
content-machine workflow docs, a multi-account operational guide with safety limits, the
data-brain vs reasoning-brain architecture decision, and the v0.3 changelog with known
limitations.

## Slice plan (smallest complete vertical slices first)

1. MCP registration and doctor check. Done in this branch.
2. Content-machine persistence: agent-authored, keyless, provenance-stamped save tools plus
   the minimal data models for angles, an idea bank that allows many ideas per source, and a
   Week 01 to 04 monthly plan. Retire the internal-LLM dependency from the ideas path.
3. Minimal multi-account slice: an accounts model, sticky channel-to-account assignment,
   isolated session per account, and honest sequential-across-accounts sync with per-account
   cooldown. Document the parallelism limit.
4. UI: finish the migration, rework the dashboard into the workflow, implement the topbar
   primary-action slot, close the state gaps.
5. Docs, tests, release evidence throughout, then a v0.3 dogfood pass.

Decision record: where several approaches were reasonable, v0.3 takes the simplest reversible
one that satisfies the thesis. Notably, multi-account sync runs accounts sequentially with
isolated sessions rather than truly parallel, because true cross-account parallelism requires
multiple sidecars or a multi-session sidecar with per-account locks, which is a larger and
riskier change than a minimal useful slice should carry.
