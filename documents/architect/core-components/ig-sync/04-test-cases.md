# ig-sync: test cases

How to run these: the sidecar must be up. From the repo root, `npm run ig:service` starts it (the wrapper loads `.env.local` and execs the module); it binds `127.0.0.1:8765` only. `.env.local` needs `IG_SERVICE_TOKEN` (at least 16 chars, shared with Node) and, for anything past `/health`, a real `IG_USERNAME`/`IG_PASSWORD` for a burner account, never one you care about; the account can be challenged or banned. Do the first login with the `curl` sequence in `services/ig/README.md` (`/login`, then `/two-factor` or `/challenge/resolve` as asked). For the app side, start the dev server and open `http://localhost:3001` for the behavior and browse-e2e cases. Offline unit and integration tests run with `uv run pytest` in `services/ig/` (150+, no network) and `vitest` for the Node suite, covering `sync-engine`, `ig/client`, and `sync-actions` against a temporary SQLite database. Cases marked `live` in the Needs column need a real Instagram account and cannot be exercised offline; they are the burner-holder's steps. Browse-e2e cases are driven with the `browse` skill against the running dev server, per `references/browse-e2e-qa.md`; none of the `data-testid` values the one journey below needs exist in the current markup yet, so that case is blocked on adding them first.

## 4. security-lite

| ID | P | Threat | Claim | Setup | Steps | Expected | Result |
| --- | --- | --- | --- | --- | --- | --- | --- |
| SEC-01 | P1 | Secret handling | The sidecar refuses to start on a missing or empty required config value, exit 78 `EX_CONFIG`, rather than booting half-configured. | `.env.local` with `IG_SERVICE_TOKEN` unset or under 16 chars. | 1. `npm run ig:service`. | The process exits 78 with a message naming the bad variable; port 8765 never opens. | not run |

| SEC-03 | P1 | Sidecar shared token | Every data route requires `X-IG-Token`; a missing or wrong token is refused, and a mismatch between the two processes surfaces on the Node side as its own error, not an Instagram error. | Sidecar up. | 1. Call `/profile?handle=x` with no token.<br>2. Call it again with a wrong token. | 401 `{"error":{"code":"IG_UNAUTHORIZED", ...}}` both times; the Node client maps a 401 to `IG_SERVICE_UNAUTHORIZED`, never treating it as an Instagram-side failure. | not run |
| SEC-04 | P2 | Secret handling | A non-loopback `IG_SERVICE_HOST` is refused at boot; the service binds loopback only, so nothing off the machine can reach it even with the token. | `IG_SERVICE_HOST=0.0.0.0`. | 1. Start the sidecar. | It refuses at boot with the loopback-only message; port 8765 never opens on a non-loopback interface. | not run |

Security-lite has no rows for a license gate or cross-tenant leakage: ig-sync has no license check of its own, and crowsnest is single-user with no tenants. "No buyer data leaving the box" is covered indirectly by SEC-04 (loopback binding); ig-sync's only outbound call is to Instagram itself, the intended destination for channel data, so there is no separate leak path to test.
