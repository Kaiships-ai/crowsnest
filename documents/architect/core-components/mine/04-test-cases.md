# mine: test cases

Result markers: 🟢 pass, 🔴 bug, 🟡 blocked (missing dependency named in the cell). Rows still reading "not run" were not driven in QA round 1.

How to run these: start the dev server and open `http://localhost:3001` (never `127.0.0.1`) for the behavior and browse-e2e cases. Seed one tracked channel; for a full run mark it own (or use the picker's "This is me" from a fresh database). Route and action cases run with `vitest` against a temporary SQLite database, covering `own-channel.ts`, `planned-posts.ts`, `planned-post-actions.ts`, `channel-actions.ts`, and `graph-actions.ts`; the Graph client itself is mocked in those tests, so no live Instagram Graph token is required for that lens. For the behavior and browse-e2e lenses, a Graph token that has measured the account at least once is needed to exercise the connected dashboard state; clearing or corrupting `IG_GRAPH_TOKEN`/`IG_GRAPH_USER_ID` in `.env.local` and restarting is how the connect panel and gated states are reached. Seed a handful of planned posts spread across a draft with no date, a scheduled future date, and a scheduled past date, plus one plan carrying a script and one marked published, so the calendar cells exercise every state. Needs column values: `mouse` and `keyboard` are the input; `graph-invalid` means the token is cleared or rejected; `graph-measured` means the account was measured at least once before; `second-tab` is a second tab on the same session, not a second browser.

Browse-e2e cases are driven with the `browse` skill against the running dev server, per `references/browse-e2e-qa.md`. The calendar and plan-dialog surfaces already carry `data-testid` attributes (`mine-calendar-day`, `mine-calendar-plan-day`, `mine-calendar-mark-published`, `mine-plan-delete`, `plan-dialog-title`, `plan-dialog-save`, `own-channel-picker-choose`, and the calendar cell-state markers), and `scripts/e2e/mine-e2e-02.sh` is checked in. The dashboard, tabs, connect panel, and posts and weekday surfaces do not carry testids yet, so the journeys that touch them name the testid they will need and note it is not present; those gaps are filed as one `test-coverage` row in `05-backlog-to-enhance.md`. All rows read `not run`: this is an authoring pass to the coverage mandate, and a later QA round drives them.

## 3. browse-e2e

Coverage: mine has six built (`●`) features (2, 3, 4, 5, 6, 7) and one happy-path journey each, below. Corner-case types covered, five distinct: `empty` (E2E-07), `auth` (E2E-08), `invalid` (E2E-09), `stale` (E2E-10), `boundary` (E2E-11).

Types not given a row, with the reason:

- `failure`: the failing paths on this page (a mid-sequence plan-edit failure, B-04; a measurement account or posts call failing) need fault injection the seeded fixture cannot force from the browser, and are exercised at the action layer instead (route-and-action ACTION-10-adjacent, ACTION-13).
- `network`: mine's only external call is the Graph API; a mid-measurement network drop is a `live` path exercised at the action layer (ACTION-12, ACTION-13), not through `browse`.

- `repeat`: re-running a measurement upserts rather than duplicating (feature 7), but that is a `live` Graph path; the offline upsert behavior is covered at the action layer.
