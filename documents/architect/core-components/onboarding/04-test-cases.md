# onboarding: test cases

How to run these: onboarding spans a terminal half and an in-app half, so the setup differs by section. The terminal cases need a machine with the Kit installed and a cached license (`kai login` already run), on a real interactive terminal, a TTY, because the known defects only reproduce there, not under `kai kit init < answers`. The in-app cases need the dev server started, opened at `http://localhost:3001/first-run` (never `127.0.0.1`); to exercise the gate you need to control two facts, `app_settings.first_run_completed` and whether any `channels` row exists, and to reset between runs use Settings' "Replay first run", which clears the flag. The connect step needs the Instagram sidecar reachable (or deliberately down) and a set of real credentials that will accept, two factor, or challenge on demand. The pure logic tests (`src/server/queries/first-run-gate.test.ts`, `src/components/first-run/onboarding-view.test.ts`) run offline with `vitest`, no database and no browser. Browse-e2e cases are driven with the `browse` skill against the running dev server, per `references/browse-e2e-qa.md`; none of the `data-testid` values the one journey below needs exist in the current markup yet, so that case is blocked on adding them first.

Security-lite has no rows for the license gate, the sidecar shared token, or cross-tenant leakage: the license check (`readEntitlement`) is owned by the Kit CLI, not onboarding; the sidecar shared token is owned and covered by [ig-sync](../ig-sync/04-test-cases.md#4-security-lite); and crowsnest is single-user with no tenants. Onboarding's own security-lite surface is the two secret prompts above.
