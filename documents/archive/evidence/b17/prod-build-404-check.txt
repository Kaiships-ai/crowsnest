B-17: a missing videoId on /feed/[videoId] must return HTTP 404, not 200.

Verified with a production build (npm run build && npm run start), scripts/verify-videodetail-404.sh:

BEFORE (unfixed, main HEAD 851249d):
  bad videoId  -> 200 (want 404)
  real videoId -> 200 (want 200)
  FAIL

AFTER (fixed, this branch):
  bad videoId  -> 404 (want 404)
  real videoId -> 200 (want 200)
  PASS

Route URL integrity after the fix (all 200, route groups are URL transparent):
  /  /feed  /vault  /ideas  /settings  /channels  /logs  /runs  /mine  /persona  -> all 200

Root cause: the shell-wide loading.tsx sat at src/app/(shell)/loading.tsx, an ancestor
Suspense boundary that wrapped every route under (shell) including feed/[videoId]. When the
page suspended on its first await (getCachedVideoDetail), the shell flushed a 200 before
notFound() could set the status. The B-14 fix scoped the feed list's own loading into
(list)/ but left this higher (shell) ancestor.

Fix: moved the generic loading and every non-feed route into a (loaded) route group, so the
loading boundary no longer wraps feed. feed/[videoId] now has no ancestor loading boundary,
so notFound() runs before any streaming and the 404 status commits. The non-feed routes keep
the same generic skeleton via (loaded)/loading.tsx. URLs are unchanged (route groups do not
affect the path).
