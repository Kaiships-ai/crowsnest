## Correction to the brief

I was told the dev database is "push/bootstrap based, not migration tracked, so `db:migrate`
replays from 0000 and fails". That is not what is happening, and the difference matters because
it turns an unfixable-looking trap into a one statement fix.

The dev database **is** migration tracked. It has a `__drizzle_migrations` table with 11 rows.
There are 14 migration files on disk. Migrations 0011, 0012 and 0013 were applied by hand with
`sqlite3 data/crowsnest.db < drizzle/NNNN.sql`, which writes the DDL but never records the hash,
so drizzle still believes they are pending. `db:migrate` does not replay from 0000. It replays
from 0011 and dies on the first `CREATE TABLE` that already exists.

Proof, run against a `.backup` copy so the live database was never touched:

```
=== copy migrations recorded: 11 ===
SqliteError: table `secrets` already exists
    at main (src/server/db/migrate.ts:33:3)
```

A fresh clone is fine. I pointed `CROWSNEST_DB_PATH` at an empty path and got all 14 migrations
and 29 tables, an identical table set to the real database. So the README quickstart is correct
for a new machine and broken only on this one.

# Findings

## Blocker

### 1. `db:migrate` is broken on the dev database, and every hand applied migration digs the hole deeper

`src/server/db/migrate.ts`, `drizzle/`, `data/crowsnest.db`

The workaround (apply DDL by hand) is what causes the breakage. Each hand applied file widens the
gap between what the database contains and what drizzle thinks it contains. At 3 of 14 the tool is
unusable; nothing stops that reaching 10 of 14.

The cost is not just the broken command. It is that `db:migrate` is the documented step 3 of the
README quickstart, so the one command that verifies your schema matches the repo is the one command
nobody on this machine can run. Schema drift now has no detector.

Fix, one statement. Drizzle's `hash` column is plain sha256 of the migration file, which I verified
against the recorded row for 0000 (`e16abf2aa2f4` matches `shasum -a 256 drizzle/0000_complete_morlocks.sql`).
Record the three that were applied by hand:

```sql
INSERT INTO __drizzle_migrations (hash, created_at) VALUES
  ('16fe6016fd99633bdbe22c322565f78e03cd7af2b5bf7e70ff9821e6089643d1', 1785510050432),
  ('2cbeb50eb7dcdd63220262a4f1f4e6d6f7edf1378df8fb0a8e9e111628320d57', 1785510050433),
  ('976cc776ac20b58e4967f3be2e726bb559fca57d2344e5b82df6555a48376e0c', 1785510050434);
```

Those hashes are the real sha256 of `0011_dapper_scrambler.sql`, `0012_cool_mauler.sql` and
`0013_frame_pass_jobs.sql`. The `created_at` values only need to be increasing and later than the
last recorded row (1785510050431).

Verify on a `.backup` copy first, then on the real file. After that `db:migrate` is the normal
path again and the hand application habit should stop.

### 2. `npm run lint` is red on main, so the documented pre-commit gate gates nothing

`src/components/channels/channel-card.tsx:138-146`

README line 226 lists `npm run lint  # No ESLint errors` as a thing to confirm before committing.
It currently reports 9 errors. Scoped to `src` it still reports 4, all in one file, all
`react-hooks/refs`:

```
138:14  error  Cannot access refs during render
140:24  error  Cannot access refs during render
145:17  error  Cannot access refs during render
146:17  error  Cannot access refs during render
```

A gate that is already failing cannot tell anyone they broke something. A developer who adds a
fifth error sees "5 problems" and has no way to know four were already there.

The trigger is the dnd-kit `useSortable` return being spread during render
(`sortable.setNodeRef`, `sortable.attributes`, `sortable.listeners`), which is dnd-kit's documented
usage. React 19's ref lint rules flag it anyway.

Fix: add a scoped disable on the `ChannelCardLive` block with a comment naming dnd-kit as the
reason, or lift the spread. Either way, get to zero, then keep it there. If the rule is judged a
false positive for this library, turn it off deliberately in `eslint.config.mjs` rather than
leaving four standing errors as ambient noise.

## High

### 3. The README tells you to expect 4 typecheck errors that no longer exist

`README.md:229`

> `npx tsc --noEmit` has a known baseline of 4 pre-existing errors in `llm/client.test.ts`,
> `analyze.test.ts` and `remix.test.ts`.

`npm run typecheck` now exits 0 with no output. The baseline is gone.

This is worse than a stale line. It instructs the next developer to wave off up to four real type

### 4. Two env knobs that the repo cannot run without on another machine point at `/Users/kienbeovl/`

`src/server/services/claude-task.ts:28`, `src/server/services/watch-frames.ts:17`

```
claude-task.ts:28   /Users/kienbeovl/.local/bin/claude
watch-frames.ts:17  /Users/kienbeovl/.claude/plugins/cache/claude-video/watch/0.2.0/skills/watch/scripts/watch.py
```

These are the only two hardcoded user paths in the whole tree (I swept `src`, `scripts`,
`services` and every config file, with the sweep proven against these two known hits before
trusting it). Both have env overrides, `CLAUDE_BINARY_PATH` and `WATCH_SCRIPT_PATH`, and neither
override is mentioned in `.env.example` or the README, so a second machine gets a spawn failure
with no pointer to the knob that fixes it.

Fix: resolve the binary from PATH by default (`claude`) and fall back to the absolute path, and
add both variables to `.env.example` with a line saying what breaks when they are wrong. The frame
pass is the feature that depends on them, so name it.

### 5. Fifteen env knobs the code reads are absent from `.env.example`

`.env.example`, `src/server/config.ts`

`.env.example` lists 24 variables. These are read by code and documented nowhere in it:

```
VIEW_COUNT_ENRICH_PER_CHANNEL   SYNC_MAX_RETRIES        SYNC_RETRY_BASE_MS
CLAUDE_BINARY_PATH              WATCH_SCRIPT_PATH       WHISPER_CPP_BIN_PATH
WHISPER_MODEL_PATH              GROQ_API_KEY            CROWSNEST_INGEST_URL
IG_SESSIONID                    IG_SERVICE_HOST         IG_SERVICE_PORT
IG_LOCALE                       IG_COUNTRY              IG_TZ_OFFSET_SECONDS
```

`VIEW_COUNT_ENRICH_PER_CHANNEL` is the on switch for a feature shipped this session. It is in
`config.ts` with a careful 12 line comment explaining that setting it below 12 quietly narrows the
scoring baseline. None of that reaches the template a developer actually copies.

Fix: bring the schema and the template into agreement. `config.ts` is the source of truth for 20
of them; the rest live outside it (see finding 9). A test that asserts every key in the zod schema
appears in `.env.example` would stop this drifting again.

## Medium

### 6. A fully passing test run prints 495 lines, 481 of which are JSON logs

`src/test/setup-env.ts`, `src/server/lib/logger.ts:24`

Runtime is not the problem. 1197 tests in 5.3 seconds is good, and the brief's concern about
`sync-engine.test.ts` being slow does not hold up: at 108 KB it is the largest test file in the
repo, 77 tests across 19 describe blocks, and the whole suite still finishes in seconds.

Legibility is the problem. On a green run you get 481 lines like this:

```
{"ts":"...","level":"warn","event":"frame_pass.failed","code":"FRAME_EXTRACT_FAILED",...}
{"ts":"...","level":"error","event":"ig.action.unexpected","error":"boom"}
```

Those are tests exercising their error paths correctly. But a real failure has to be found by
scrolling past several hundred lines of expected `error` and `warn` output, and `error` level
noise on a passing run trains people to ignore the word.

Fix, one line in `src/test/setup-env.ts` next to the two defaults already there:

```ts
process.env.LOG_LEVEL ??= "error";
```

`activeLevel()` in `logger.ts:24` reads `process.env.LOG_LEVEL` on every call, so this takes effect
without touching the logger. I checked that no test sets or asserts on `LOG_LEVEL`, and
`logger.test.ts` asserts on the database sink rather than console output, so nothing regresses.
Use `"warn"` if the warn lines are wanted. The `??=` keeps a one-off `LOG_LEVEL=debug npm run test`
working.

### 7. `npm run lint` has no path scope, so it lints untracked scratch directories

`package.json:9`, `eslint.config.mjs`

`"lint": "eslint"` with no argument walks the whole repo. Five of the nine errors come from
`claude-animation/` and `Crowsnest UI Mockups/`, mostly untracked scratch work: a bundled design
system file, `image-slot.js`, `support.js`, some GSAP effects.

So the gate reports failures in files that are not the product and in some cases not even in git.

Fix: add them to `globalIgnores` in `eslint.config.mjs`, or scope the script to `eslint src scripts`.
Scoping the script is the smaller change and it keeps future scratch directories out by default.

### 8. No Node version pin anywhere, with a native module in the dependency tree

`package.json`

There is no `engines` field, no `.nvmrc` and no `.node-version`. `better-sqlite3` is a native
addon, so the wrong Node major gives an ABI mismatch at require time, and the error names a `.node`
file rather than the version mismatch that caused it.

This machine has node@20, node@22 and node@24 installed under Homebrew. Nothing records which one
the lockfile was built against.

Fix: add `"engines": { "node": ">=22 <23" }` to `package.json` and an `.nvmrc` with the matching
version. Pick the version that `package-lock.json` was actually built with.

### 9. Ten env knobs bypass the central config schema that exists to catch exactly this

`src/server/config.ts`

The file's own header says it is "the single place this app reads `process.env`". It is not. These
are read directly and never validated:

| Variable | Read at |
| --- | --- |
| `CLAUDE_MODEL` | `src/server/llm/client.ts:63` |
| `LLM_BASE_URL` | `src/server/llm/client.ts:220,236`, `src/app/(shell)/page.tsx:35`, `src/app/(shell)/feed/[videoId]/remix/page.tsx:15` |
| `LOG_LEVEL` | `src/server/lib/logger.ts:25` |
| `PORT`, `CROWSNEST_INGEST_URL` | `src/server/sidecar/control.ts:11,12` |
| `YTDLP_BIN_PATH` | `src/server/providers/ytdlp.ts:46`, `src/server/lib/exec.ts:56`, `src/app/(shell)/settings/page.tsx:57` |
| `WHISPER_MODEL_PATH`, `WHISPER_CPP_BIN_PATH` | `src/server/transcribe/whispercpp.ts:14,18` |
| `CLAUDE_BINARY_PATH` | `src/server/services/claude-task.ts:34` |
| `WATCH_SCRIPT_PATH` | `src/server/services/watch-frames.ts:42` |

Two schema-owned variables are also re-read directly with their defaults restated, so a default can
now drift in two places: `MEDIA_ROOT` (`config.ts:58` and `frame-pass.ts:31`) and `CROWSNEST_DB_PATH`
(`config.ts:78`, `db/index.ts:7`, `db/migrate.ts:15`, `scripts/backup-db.ts:91`).

The header comment explains that the previous provider layer silently dropped providers whose env
key was missing, and that "that failure mode is gone". For the ten above it is not gone.

Fix: move them into the zod schema. `YTDLP_BIN_PATH` and the whisper paths especially, since a typo
there surfaces as a missing binary at click time, which is the exact failure the schema was built to
convert into a boot error. The db path re-reads are deliberate (`db/index.ts` loads before config),
so leave those but hoist the literal `"data/crowsnest.db"` into one shared constant.

### 10. Two runtimes, no single command, and the gotcha that makes it awkward is undocumented

`package.json`, `scripts/ig-service.sh`, `services/ig/README.md`

Starting Crowsnest means two terminals: `npm run ig:service` and `npm run dev`. The README is honest
about it (step 5 says "separate terminal"), and `scripts/ig-service.sh` has a good comment explaining
why it execs rather than sources `.env.local`.

What is missing is the operational fact that makes this awkward in practice: a dev server started
from a plain agent shell gets reaped after a minute or two, so it needs its own persistent pane. That
is recorded in `docs/superpowers/plans/*.md` and in nobody's onboarding path. Same for browsing via
`localhost` rather than `127.0.0.1`, which is a Next 16 Server Actions origin check and currently
appears only in passing in the README.

Fix: a short "Running it" section in the README with both facts stated plainly, plus a `dev:all`
script for the ordinary case. Do not reach for `concurrently` as the only answer, because the
reaping problem is about process lifetime rather than parallelism, so the note matters more than
the script.

## Low

### 11. `SYNC_STALL_SECONDS` is a hardcoded constant that two derived thresholds hang off

`src/server/services/sync-types.ts:116`, `src/server/services/sync-engine.ts:100,101`

```ts
export const SYNC_STALL_SECONDS = 90;
const HEARTBEAT_MAX_SILENCE_MS = (SYNC_STALL_SECONDS * 1000) / 3;
const LOCK_STALE_MS = SYNC_STALL_SECONDS * 1000 * 10;
```

The derivation is well commented and the arithmetic is deliberate. The issue is only that view count
enrichment can push a run past 90 seconds of apparent silence, and the sole way to test that
interaction is to edit source. Every other sync knob (`SYNC_MAX_RETRIES`, `SYNC_RETRY_BASE_MS`,
`MAX_ITEMS_PER_SYNC`) is already env driven.

Fix: `SYNC_STALL_SECONDS: intWithDefault(90, 10, 3600)` in the schema, keep both derivations as they
are. Low because the default is sound and nothing is broken today.

### 12. No CONTRIBUTING.md and no CHANGELOG.md

Repo root.

For a private solo project this is defensible, and the README carries real operational knowledge
that most projects lack (the testing conventions section is genuinely good). Noting it because the
"Testing conventions" block in the README is doing CONTRIBUTING's job at 30 lines and will keep
growing.

Fix: leave it until a second person touches the repo, then split.

Overall: **6/10**. The repo is in better shape than the finding count suggests. The tests are fast
and comprehensive, typecheck is clean, and the prose explains rationale better than most codebases.
What is weak is the gap between what the docs promise and what the commands do: two of the four
documented pre-commit gates are wrong (lint is red, typecheck's baseline is stale), and the
documented database step fails on the machine it is run from.

No prior `/plan-devex-review` exists for this project, so there is no boomerang comparison.
